# Production deployment recommendations (WikiRAG)

**Infrastructure & scale.** For WikiRAG, **ChromaDB’s embedded `PersistentClient`** fits a single host well but becomes a bottleneck when multiple app replicas need concurrent writes or local disk I/O saturates. **Pinecone** or **Weaviate** gives a managed vector index with metadata filters aligned to your `entity_type` / `title` fields—expect a one‑time re‑embed and bulk upsert, not a live file sync. Migrate **`ingestion.db` and `cache.db`** to **PostgreSQL** for backups, replication, and schema migrations (`alembic`); keep vectors in the dedicated store unless you standardize on **pgvector** in the same cluster. **Containerize** the UI, workers, and job runners with **Docker**, then deploy on **AWS ECS/Fargate**, **GCP Cloud Run**, or **GKE** with secrets from the cloud provider’s secret manager. Colocate the **LLM on GPU** (**e.g. AWS g5 / L4, GCP A100 or L4 nodes**) in the same region as your vector API, and run routing plus retrieval on CPU tiers so autoscaling does not starve generation.

**LLM & embeddings.** **Ollama** is ideal for local dev; in production many teams swap it for **vLLM** or **Hugging Face TGI** behind an OpenAI‑compatible route for continuous batching, paged attention, and clearer SLOs under concurrency. Upgrading from **llama3.2** to **Llama 3 70B** or **Mistral 7B** usually improves comparison answers and reduces hedging—budget **GPU VRAM** accordingly or use **AWQ/GPTQ** through vLLM. Your **`embedder.py` / `vectorstore`** seam maps cleanly to **`text-embedding-3-small`** via **OpenAI** when latency and multilingual quality outweigh strict on‑prem privacy; batch chunk embeddings during ingest and respect TPM limits. If you switch providers, **re‑index everything** and version the collection (e.g. `wiki_rag_v2_openai`) so rollback is a config flip. Verify **dimension and distance** (cosine vs dot product) match the hosted index spec so scores stay comparable to today’s Chroma cosine setup.

**Retrieval quality.** Keep the current heuristic reranker for cost‑free wins, then add a **cross‑encoder** rerank (e.g. **MS MARCO–style** or **BGE reranker**) on the top 30–50 vector hits before truncation, batched on GPU if you need sub‑100 ms overhead. Introduce **query expansion** (one cheap LLM call or curated synonyms) so short names in the user query pull in chunks that only spell out full legal titles in body text. Add **hybrid retrieval**: **BM25** plus dense vectors with **RRF** or weighted fusion (**OpenSearch**, **Elasticsearch**, or Weaviate hybrid) to stabilize keyword‑heavy questions where embeddings alone drift. Adopt **RAGAS** on a frozen eval set (50–100 QA pairs grounded in your 40 articles) to track faithfulness, context precision, and context recall each deploy. Use those metrics to tune **`TOP_K_*`**, **`MAX_CONTEXT_WORDS`**, and rerank thresholds instead of tuning by eye.

**Reliability & monitoring.** Wire **LangSmith** or **Langfuse** to trace full turns: router label, cache hit/miss, comparison vs standard path, Chroma/Pinecone latency, token usage, and model id so incidents separate “bad retrieval” from “bad generation.” Promote **response caching** to **Redis** with TTL and stamped‑out keys from your existing **`hash_query`** logic so multiple Streamlit/API replicas share one hot cache under burst traffic. Persist **thumbs up/down** (and optional comment) in Postgres keyed to `message_id` / query hash to feed eval sets and on‑call triage. Run **ingestion** as **Celery** (or **RQ**) tasks—fetch, parse, chunk, embed, upsert—with retries per article so the chat tier never blocks on Wikipedia throttles. For **multi‑user** exposure, add **API gateway rate limits** (per IP or API key), payload caps, and queue‑depth alerts on workers so overload backs off cleanly instead of OOM‑killing GPU inference pods.
